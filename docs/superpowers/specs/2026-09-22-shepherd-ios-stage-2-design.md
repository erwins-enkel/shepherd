## Intent and baseline

Provide an iOS app that connects to an existing Shepherd server, manages remote profiles and authentication, lists live sessions, and reads a selected session. Reuse the application layer extracted in Stage 1 rather than reproduce its state or networking. No terminal or session-changing action belongs in this stage. Success is a usable isolated iOS sign-in/list/detail flow, simulator build and executed tests, unchanged Mac behavior, and a read-only live smoke with verified cleanup of only the test's own tokens.

| Option | Consequences | Proposal |

## Composition and profile/authentication flow

One app-lifetime `AppModel` owns profiles, activation, selection and routing. Before restoring a saved profile, register `SidebarModel.self` and `DetailModel.self` directly with the existing public `AppModel.register`. Do not call `StreamRegistrations.installAll` or configure unused Mac presentation seams. Tests establish that repeated registration creates one instance of each extension per activation and that terminal/notifications/write-oriented extensions are absent.

**Required shared prerequisite found by review:** At the merged baseline, `AppModel.activate` constructs `SessionStore(client:)` without its optional `events` argument. That initializer has no socket; only the convenience profile initializer supplies one. Correct activation to construct one audited `ShepherdClient`, then `SessionStore(client: client, events: EventStream(client: client))`. Do not switch to the convenience initializer and lose the injected request audit. This is a narrowly scoped prerequisite within the Stage-2 PR, owned by the integrator in `native/Sources/ShepherdAppCore/App/AppModel.swift` with a new `native/Tests/ShepherdAppCoreTests/AppModelEventCompositionTests.swift`. It restores intended shared behavior for both hosts, so require Mac and simulator regression evidence for this actual change, not a repeat of unrelated historical gates. A composition test must exercise AppModel activation through an audited client and fake server/socket, observe a pushed session update without a manual refresh, prove one socket and presence delivery, then prove teardown/profile switch stops the old delivery. Tests that instantiate SessionStore directly cannot verify this wiring.

Supply an iOS-owned passive `NotificationEnvironment` because AppModel requires one. It has no system notification delivery or authorization requests; no `NotificationsModel` is registered. Its focus adapter is platform-host code, not a new core platform dependency. Lifecycle presence is owned exclusively by the iOS host.

Use `beginRemoteLogin(name:address:)` / `addRemoteProfile(name:address:)` for parsing and validation. `RemoteServerForm` is intentionally internal; these public APIs already call its normalization. Do not duplicate normalization, expose it just for UI convenience or bypass ShepherdKit's HTTPS/loopback/`.ts.net` policy. Review iOS transport configuration against that policy in the implementation plan; do not add a blanket ATS bypass. Keep existing profile/defaults/credential-key spellings: app sandbox separation supplies the platform boundary.

Saved remote profiles support selection, reconnection, adding and removal through AppModel. No “Run on this Mac” or local profile creation. The login sheet calls `signIn(profile:password:)`, uses `LoginSheetState` and `ShepherdErrorCopy`, blocks duplicate submission/dismissal while busy, clears its password when finished or dismissed, and closes only if it still owns the matching login route. A successful login may already have routed first-run state; an outgoing completion must not dismiss that replacement sheet or reactivate a different profile.

Use the existing public login closure to name ordinary tokens with `ProfileSetup.tokenName(prefix: "Shepherd for iOS (")`; isolated live tokens use a unique per-run test name. Normal app launches use `KeychainCredentialStore`; automated launches must select memory storage before constructing AppModel. No passwords in persistent state or logs. Existing `ProfileSetup.login` mints full-scope tokens: the stage's read-only promise describes session operations and enforced test access, not a new server token-scope policy. Do not silently change token scope or contract.

Sign-out uses `signOutActiveReporting`; removal uses `remove`. Preserve warnings for errors these APIs actually surface, but describe completion only as local sign-out/profile removal. Production `ProfileSetup.logout` currently swallows refused revocation responses/transport errors and clears local credentials; `remove` also discards logout errors. Therefore Stage 2 must not claim confirmed server-side revocation or promise a failure warning that these APIs cannot supply. Show a localized local-sign-out notice that remote revocation is unverified; use fake transport tests against the production logout path to pin that distinction. Changing shared token-revocation/reporting semantics is a separately proposed authentication follow-up, not an unreviewed Mac behavior change. This limitation does not relax the stronger mandatory live-test cleanup contract below. `.firstRunPending` shows a localized explanation that server setup must be completed through an existing supported client, with profile switching/sign-out available; it does not resolve first run or present a Mac folder picker. An unusable profile, expired credential, incompatible server, empty result and network failure must have distinct recoverable states using existing routing and banner policy.

## Session list and read-only detail

Use `SidebarModel.sessions` and `rendered(_:)` for list membership/status. Initially use its all-sessions lens; do not add Herd stage grouping or shared lens UI without their later feature wiring. Rows show existing identity, name, status and repository/branch information where provided. No duplicate filtering/status algorithms. Expose loading, connected-empty, offline-with-last-known-data and authentication-required states honestly.

Use `NavigationSplitView` with iPhone stack adaptation and an iPad detail column. Selection remains `AppModel.selectedSessionID`; reconcile against current store IDs with the existing helper. Changing profiles clears the old selection. A removed/archived session that leaves the visible list does not keep an actionable stale detail. Unknown generated enum values render through existing fallback rules instead of crashing. Controls support accessibility labels, Dynamic Type and EN/DE copy.

The first detail contains session identity/name, rendered status, available repository/branch metadata, existing prompt text and activity. It consumes SessionStore's generated Session values and `DetailModel.activity`; initial activity loading uses `poll(.activity, session:)`, whose existing event tap refreshes activity without a new timer. Key view tasks by `DetailTaskKey` including model identity, cancel on navigation, and read only the current activation's model. Show loading, empty, failed/retry and refreshed data states; preserve the model's activity ordering rather than independently invent sorting semantics.

Do not install a generic detail registry containing hidden terminal/actions. No PTY connection, terminal UI/input, composer, session create/archive/interrupt/rename, plan approval, merge, settings writes, queue recomputation, file edits, or server setup mutations. Diff/files/git detail views remain proposed follow-up scope. Authentication and own-token lifecycle are the explicit exceptions to read-only data operations.

## Foreground, background and event ownership

Retain AppModel and its current SessionStore across temporary inactive/background phases. Forward ordered presence changes through `SessionStore.setActive(_:)`; this is the existing temporary quieting API. Do not call `stop()` then `start()` on the same store: stopped stores are terminal. Do not use `deactivate()` as background suspension because it clears active-profile persistence and selection. `restoreActiveProfile()` runs once at initial launch, not on every foreground transition.

On return to active, use the current store only, restore active presence, call existing `app.retry()` for session/health reconciliation and reload visible activity. The existing connection loop owns reconnect and SessionStore snapshot recovery; SidebarModel has its own reconnect refresh. DetailModel does not have a reconnect observer: activity polling loads once and subsequent updates normally require activity events. The iOS lifecycle/detail coordinator must observe each transition of the current store back to `.live` and reload the currently visible activity, including after a failed earlier foreground reload. Coalesce redundant recovery loads and guard activation, selected-session and model identity so a missed activity event during a gap cannot leave detail stale indefinitely. No timer or second socket is needed. This design does not promise immediate reconnect through a nonexistent SessionStore API or any background processing entitlement. Loss of the socket while suspended is recovered on foreground by existing reconnect plus refresh; tests must prove eventual fresh data and surfaced failure/retry.

The iOS lifecycle coordinator owns its observation/tasks, orders rapid scene transitions and re-applies current phase when a new store becomes live. Generation/store identity checks prevent an old async presence/refresh completion from changing the new activation. Actual sign-out/removal/profile switch uses AppModel's existing generation increment, extension teardown-before-store-stop and fresh-store creation. Full lifecycle ownership stays in core; iOS only adapts scene events.

## Isolation and live-smoke contract

Recognize the existing `-ShepherdIsolated 1` launch convention and plain/test-runner isolation environment spellings before app construction. Tests use unique throwaway defaults plus `InMemoryCredentialStore`; failure to create isolated storage fails closed, never falls back to standard defaults or Keychain. Ordinary deterministic CI uses fake HTTP/event fixtures and no operator credentials. Do not read operator profiles, start notification prompts, enable either spelling of `SHEPHERD_KEYCHAIN_TESTS`, or launch automatically without isolation.

Future local live execution may read only `~/.config/shepherd/codex/live-smoke.json`, exactly as named by the operator. Planning does not read it. Never print its values, place credentials on command lines, commit them, or include them in issues/artifacts. Use the existing isolated harness's secret-handling pattern with only the necessary values reaching the owned test process; no broad config/environment dump.

Each live run owns its unique temporary `Shepherd UI test (…)` token and ID. Revoke that exact owned token and prove that it yields HTTP 401 before terminating the app; iOS termination callbacks are not a reliable cleanup mechanism. Provide an explicit in-app test cleanup handshake plus a harness cleanup path for failures/cancellation. Do not sweep by a shared name, revoke another run's token or touch operator credentials. If cleanup cannot be verified, report an unmet gate with the nonsecret run identifier; never claim success. Fake-server tests cover cleanup failure and interrupted flows without intentionally leaking live tokens.

Use `ReadOnlyRequestAudit` on the activated test store, disallow writes and `getBranchStatus` even though that operation is a GET with git-fetch side effects. Keep queue recomputation and terminal input disabled. Authentication's separate client is limited to login and the run's own mint/revoke lifecycle. The single event socket may send existing presence frames. Check audit counts and cleanup evidence; an empty live server can verify empty-list behavior but cannot count as successful live detail coverage.

## iPhone Duo and TestFlight beta readiness

Apple's current iPhone Duo materials describe a foldable device with a 7.6-inch inner display and 5.4-inch outer display. Apple's developer guidance says to design for size classes—compact width on the outer display and regular width on the inner display—and to avoid fixed device widths or pose-specific breakpoints. Stage 2 therefore treats Duo as a first-class adaptive target: `RootView` uses `horizontalSizeClass` and available width, compact presents stack navigation, and regular presents the session list beside read-only detail. The selection and current activity task survive compact/regular transitions. Apple also documents beta/preliminary `DeviceHinge`/`onHingeChange`, UIKit `UIHingeInteraction`/`UIHinge`, and Reserved-Region APIs; Stage 2 may use these behind availability gates for fold/occlusion-safe layout, with size-class behavior as the fallback. No device-model branch or pose-specific feature gate is introduced.

The UI matrix adds iPhone compact, Duo outer compact, Duo inner regular, Reserved-Region/fold fallback, and 12.9-inch iPad regular with hardware keyboard. It checks Dynamic Type, pointer/touch hit targets, keyboard focus and stable navigation at changing widths. This remains a shell/list/detail concern; terminal and writes remain outside Stage 2. The product page currently lists retail availability from 23 October 2026, so hardware validation is a release-target gate rather than a claim that a local device has already been tested. Apple currently points Duo development at Xcode 27.1 beta/iOS 27.1 beta; the app's iOS 18 deployment floor remains, while Duo APIs are optional and availability-gated.

Stage 2 also includes a separate TestFlight-readiness deliverable: an archive/IPA path, explicit bundle/signing/export-compliance inputs, App Store Connect test information, internal beta smoke and external-group handoff. The first external build requires the separate TestFlight review path; an Internal-Only build must not be treated as an external beta. Apple documents up to 100 internal and 10,000 external testers, a possible App Review step for the first external build, and a 90-day build lifetime. Apple account credentials, certificates, provisioning profiles and upload API keys stay outside the repository, issue and test logs. TestFlight distribution is not a substitute for the isolated read-only live smoke or its owned-token HTTP-401 cleanup.
